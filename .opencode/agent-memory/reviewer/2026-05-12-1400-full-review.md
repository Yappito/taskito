## High Severity

### 1. Module-level `automationDepth` causes silent automation suppression under concurrent requests

**File:** `src/server/services/automation-evaluator.ts:5`

```typescript
let automationDepth = 0;
```

**Issue:** `automationDepth` is a module-level mutable variable. Node.js serves concurrent requests on the same event loop, and async/await inside `executeAutomationAction` (line 70-96) allows interleaving. If request A sets `automationDepth` to 1 (inside `executeAutomationAction`) and awaits, request B calling `evaluateAutomationRules` sees `automationDepth > 0` and returns early at line 100-102, silently skipping ALL automation rules for request B.

**Failure scenario:** Two users trigger task updates simultaneously. The second user's automation rules (e.g., auto-assign, auto-archive) are silently skipped. No error is logged because the early return is intentional.

**Fix direction:** Replace the module-level variable with `AsyncLocalStorage` to isolate automation depth per request:
```typescript
import { AsyncLocalStorage } from "node:async_hooks";
const automationStorage = new AsyncLocalStorage<{ depth: number }>();
```
Then wrap `evaluateAutomationRules` body in `automationStorage.run({ depth: 0 }, ...)` and use the store's `depth` field instead of the module variable. This guarantees request isolation without changing the cascade-suppression logic.

### 2. Content-Security-Policy permits `'unsafe-eval'` globally

**File:** `next.config.ts:13`

```
script-src 'self' 'unsafe-inline' 'unsafe-eval'
```

**Issue:** `'unsafe-eval'` enables arbitrary JavaScript evaluation (`eval()`, `Function()`, `setTimeout(string)`, etc.) across the entire app. This weakens XSS protection significantly. If any injection vector exists, the attacker can execute arbitrary code despite the CSP.

**Fix direction:** Remove `'unsafe-eval'` if the app does not use code generation from strings. If Next.js/React requires it in production, add a `'strict-dynamic'` fallback or restrict via a nonce/hash for known chunks. At minimum, document why it is required. Test with `'unsafe-eval'` removed in a staging build.

### 3. Recurrence processor abort on single-rule failure loses remaining rules

**File:** `src/server/services/recurrence-processor.ts:38-78`

**Issue:** The `for` loop processes recurrence rules sequentially. If `createTaskWithNextNumber` throws for one rule (e.g., unique constraint on task number after all retries exhausted, or a foreign-key violation from a deleted sprint), the entire batch aborts. All remaining due rules in that run are skipped and their `nextDueDate` is NOT advanced, so they will be picked up on the next cron run. However, on a busy system, this could cause repeated failures and backlog.

**Fix direction:** Wrap each rule iteration in a try/catch, log the error, and continue to the next rule. Optionally advance the `nextDueDate` for the failing rule (with a reasonable increment) to prevent a permanently-failing rule from being retried every cron cycle.

## Medium Severity

### 4. In-memory rate-limit store is unbounded — memory leak

**File:** `src/lib/rate-limit.ts:22-35`

```typescript
const stores = new Map<string, RateLimitStore>();
```

**Issue:** Entries are never evicted after the window expires. Old entries persist indefinitely. For `"ai-chat"` and `"ai-provider-test"` buckets, every unique user+action pair creates a permanent entry. Over time this accumulates without bound.

**Fix direction:** Either (a) add a periodic cleanup that scans and deletes expired entries, or (b) switch to a TTL-based store (e.g., `Map` with `setTimeout` deletion, or a simple LRU cache). For production with horizontal scaling, use an external store (Redis).

### 5. Analytics date calculations use server local timezone — timezone leak

**File:** `src/server/routers/analytics.ts:6-10`

```typescript
function startOfDay(date: Date) {
  const copy = new Date(date);
  copy.setHours(0, 0, 0, 0);   // <-- uses server local timezone
  return copy;
}
```

**Issue:** `setHours()` operates in the server's local timezone. If the server is in UTC+2 and a user in UTC-5 creates a task at 20:00 UTC-5 (01:00 UTC next day), the analytics `startOfDay` treats it as the next day's task. This causes incorrect overdue detection and velocity grouping.

**Fix direction:** Use UTC methods (`setUTCHours`, `getUTCDate`, etc.) for all date calculations in analytics, or accept an explicit `timezone` parameter from the client. At minimum, document that all date calculations use server timezone.

### 6. Service worker has no update notification mechanism

**File:** `public/sw.js`

**Issue:** The service worker calls `skipWaiting()` on install and `clients.claim()` on activate, taking control of all clients immediately. But there is no message channel back to the app to notify users of available updates. After a deploy, users on the old tab/app session will not know a new version is available. The cache name `taskito-shell-v1` never changes in this code, so the activate handler's cache cleanup is a no-op.

**Fix direction:** Add a `message` event handler in the SW that listens for `SKIP_WAITING` messages. Add a version/cache-busting mechanism (e.g., include a build hash in the cache name). On the client side, listen for the `updatefound` event in the registration and surface an "Update available" prompt.

### 7. Server-side AI provider request timeout not propagated to Anthropic streaming

**File:** `src/server/services/ai/provider-anthropic.ts:109`

**Issue:** The Anthropic streaming function uses `AbortSignal.timeout(timeoutMs)` combined with the caller's signal via `AbortSignal.any()`. However, if the timeout fires mid-stream, the `finally` block at line 184 will run and `normalizeAiProviderRequestError` will wrap the abort error. The caller (stream route) will receive this as a generic "Provider request failed" error. There is no streaming-specific error handling to close the SSE stream gracefully with a proper error event. The stream just aborts mid-flow.

The OpenAI streaming provider has the identical pattern — same issue.

**Fix direction:** Catch `AbortError` specifically in the streaming functions and call `onDelta` (or a dedicated `onError` callback) to send a final SSE error event before throwing. The stream route should handle this by encoding an error SSE event before the controller closes.

### 8. Gantt-view range calculation uses `Math.min(...dates.map(...))` — stack overflow risk on large datasets

**File:** `src/components/gantt/gantt-view.tsx:32-33`

```typescript
const min = dates.length ? new Date(Math.min(...dates.map((date) => date.getTime()))) : new Date();
```

**Issue:** `Math.min(...largeArray)` spreads a potentially large number of arguments. With `limit: 100` on the task list query, this is safe today (100 tasks = 200 dates max). But if the limit is increased or removed, this will hit the JavaScript argument length limit (~125k in V8). The spread is also slightly slower than a manual reduce on large arrays.

**Fix direction:** Use `dates.reduce((min, d) => Math.min(min, d.getTime()), Infinity)` instead of spread.

### 9. Calendar view date bounds in local timezone may miss cross-timezone tasks

**File:** `src/components/calendar/calendar-view.tsx:37`

```typescript
const { data, isLoading } = trpc.task.list.useQuery({ projectId, dueDateFrom: gridStart, dueDateTo: gridEnd, ... });
```

**Issue:** `gridStart`/`gridEnd` are computed in local timezone (via `addDays` and `startOfMonth` using local `getDay()`/`setDate()`). The server interprets these dates in UTC. A task with a UTC due date of `2026-05-01T00:00:00.000Z` would be missed by a UTC-5 user viewing May because `gridEnd` in local time might be `2026-06-01T00:00:00.000-05:00` → `2026-06-01T05:00:00.000Z`, and the query filters `dueDate: { lte: gridEnd }`. The task at `2026-06-01T00:00:00.000Z` would be included since it's `< 2026-06-01T05:00:00.000Z`, so this is fine. But the first-day exclusion could happen in the other direction: a task at the end of the month in UTC might fall outside the local-timezone window.

**Fix direction:** Extend the query window by 1 day on each side to create a buffer, then filter client-side by the displayed month.

### 10. Inconsistent `executedPayload` storage between YOLO/approval paths

**File:** `src/server/services/ai/orchestrator.ts:181` and `src/server/routers/ai.ts:930`

**Issue:** Both paths store the unresolved `proposedPayload` as `executedPayload`. When the user provides an explicit payload override in `approveAction`, the resolved payload IS stored. When they don't (the common case), the unresolved payload is stored. This means `executedPayload` may contain unresolved task references (e.g., `"PROJECT-123"` instead of a cuid). The audit trail is inconsistent: some actions have resolved references, others don't. For rollback, this doesn't matter (checkpoints capture DB state), but for audit/UI display it creates confusing inconsistency.

**Fix direction:** Store the resolved payload returned by `executeAiAction` (via `resolveAiActionPayload`) in both YOLO and approval paths. The `executeAiAction` function already has the resolved payload — it should be returned or stored directly rather than re-reading `execution.proposedPayload`.

### 12. `formatHours` uses `seconds / 360` for hours display (confusing but correct)

**File:** `src/components/dashboard/dashboard-view.tsx:14`

```typescript
return `${Math.round(seconds / 360) / 10}h`;
```

This is correct (`seconds/360` = `seconds/3600*10` = `hours*10`). The intent is clear after analysis but looks like a unit error at a glance. Consider using `Math.round(hours * 10) / 10` for readability.

### 13. Recurrence `set` mutation does not validate `nextDueDate` vs `endDate`

**File:** `src/server/routers/recurrence.ts:17`

If the user sets `nextDueDate` after `endDate`, the rule will be immediately expired. The `processDueRecurrences` function handles this gracefully (filters via `OR: [{ endDate: null }, { endDate: { gte: now } }]`), but the initial state is surprising. Add a Zod `.refine()` that validates `nextDueDate <= endDate` when `endDate` is provided.

### 14. Search modal keyboard handler does not prevent ArrowUp/ArrowDown page scroll when results are empty

**File:** `src/components/ui/search-modal.tsx:185-197**

`ArrowDown` and `ArrowUp` only call `e.preventDefault()` when `resultsList.length > 0`. When results are empty (e.g., query is loading), pressing Arrow keys scrolls the page behind the modal backdrop. Add an early `e.preventDefault()` before the length check.

### 15. PWA offline banner has delayed initial state

**File:** `src/components/pwa/pwa-register.tsx:12**

`update()` is called immediately after `useState(false)`, causing one render cycle where `offline` is `false` even when the user is actually offline. The user sees the app without the banner for one frame. Not harmful, but fixable by initializing state with `!navigator.onLine` when available.

## Open Questions / Unverified Assumptions

- The `AbortSignal.any()` API (used in both streaming providers) requires Node.js ≥ 20. Verify the production Node.js version meets this requirement.
- The migration adds `Task_projectId_sprintId_idx` index in the SQL but this index is not declared in the Prisma schema. It exists only in the migration. If the schema is re-generated from scratch (e.g., `prisma db push`), this index would be lost. Either add `@@index([projectId, sprintId])` to the Task model, or ensure this migration is the canonical way to provision the DB.
- Rate limiting for `"ai-chat"` (20 req/min) and `"ai-chat-stream"` (20 req/min) use different bucket keys, so a user could send 40 AI messages per minute by alternating between the streaming and non-streaming endpoints. Verify whether this is intentional.
